02
One user model — guests and hosts are just users
Align on: unified identity, surface separation through properties not plumbing

A host who also books a vacation is one person. They get one Segment profile, one identity, one view across both surfaces. We don't split them into two separate systems — we enrich them with traits that describe what they've done on each surface.

User traits distinguish behaviour, not separate pipelines. A user profile might have has_marketplace_booking: true and has_wanderos_site: true. Customer.io uses those traits to decide which messages to send. Segment Unify stitches all their events — from wander.com, app.wander.com, mobile — into one profile automatically, as long as they log in with the same userId.

The scale difference matters for ad audiences. We expect millions of guests on the marketplace. WanderOS will be thousands of operators. The separation that matters is at the ad audience level — you don't want a "lookalike of people who booked a vacation" contaminated with property managers. That's handled through event properties and audience filters, not separate analytics systems.

Where the real separation lives Not in Segment plumbing — in Customer.io segmentation (guest streams vs host streams) and social handles (@wander for guests, @wanderos for operators). Those are the places where mixing audiences actually hurts. Segment's job is to give you one clean view of the whole person.
03
Analytics & pixel architecture
Align on: one workspace, separate sources, pixel decision is separate

Segment: one workspace, multiple sources. Segment's own guidance is to avoid splitting workspaces for product or brand separation — instead, use one workspace with separate sources (each with their own write key), labels for partitioning, and resource-scoped roles. Splitting workspaces creates a hard wall that makes cross-product questions structurally harder to answer: guest-host overlap, suppression across journeys, unified lifetime view.

Layer Recommendation Why
Workspace One workspace Keeps guest + host profiles unified. Enables cross-product lifecycle logic and suppression. Segment's recommended default.
Sources Separate sources per technical surface wander.com web, mobile app, wander backend, app.wander.com — each gets its own write key. Sources map to where code runs, not to business segments.
Profiles (Unify) One prod Unify space Single customer view across guest and host behaviour. Dev/prod separation via Segment spaces, not separate workspaces.
Access control Resource-scoped roles + labels Right people see right sources. Label sources by Product=Marketplace/Host and Env=Prod/Dev.
When would you actually split workspaces? Different legal entity, different compliance regime, different billing/admin ownership, or a deliberate choice that guest and host should never share identity or suppression logic. None of those apply to Wander today.

Pixels: keep this decision separate from analytics architecture.

One Meta pixel with custom events per surface is sufficient for now and is how most mature platforms (Airbnb included) operate. Fire Purchase on booking completion, CompleteRegistration on WanderOS signup, Lead on /listed form submit — all through one pixel, attributed to their respective campaigns.

The one real constraint Segment's Facebook Pixel destination is web device-mode only, and a single web source can only connect to one device-mode Meta pixel instance. If you ever want two different Meta pixel IDs routing through Segment, you'd need two separate web sources — not two separate workspaces. This is manageable and is a source-level decision, not a workspace-level one.

Recommended pixel setup: One pixel ID for now, custom events for guest vs. host conversions. Add a second pixel ID (WanderOS-specific) only when WanderOS runs dedicated ad campaigns that need independent audience pools — likely when there's a dedicated WanderOS marketing person.

Decision needed Will WanderOS campaigns run from shared ad accounts (one pixel, custom events) or will they get dedicated ad accounts with their own pixel IDs? This is a resourcing and campaign management question, not an architecture constraint.
04
The full tracking stack — pixels, client-side, server-side
Align on: what we actually run, measurement hygiene, proxy question

We have a larger ad tech footprint than most people realise. Here is the complete picture of what is firing for the guest marketplace today.

Client-side (browser). One Segment snippet runs on wander.com. It fans out to: Amplitude, Mixpanel, Customer.io, HubSpot, and ad pixels for Meta, TikTok, Twitter/X, Pinterest, Reddit, and LinkedIn. The mobile app also fires Segment, routing to the same destinations.

Server-side (backend). Server-to-server APIs run independently of the browser — unaffected by ad blockers or iOS privacy restrictions. These are already active:

Platform Type Status Notes
Meta Conversions API (CAPI) ✓ Active Primary + Secondary (catalog) — fires from Wander backend. iOS 14 conversions are preserved.
Google Ads Conversion API ✓ Active Server-to-server. GA4 also runs cloud-mode through Segment — no browser dependency.
Pinterest Conversions API ✓ Active Server-side via Segment.
Reddit Conversions API ✓ Active Server-side via Segment.
TikTok / Bing / LinkedIn Client pixel Active Browser-only. No server-side counterpart currently. TikTok CAPI is available if needed.
This is already in a healthy state Having CAPI active for Meta, Google, Pinterest, and Reddit means ad spend measurement has better signal than most companies of our size. Server-side conversions are unaffected by iOS privacy changes or ad blockers. This is not a problem to fix — it is a competitive advantage to protect.

Self-hosted scripts and reverse proxying.

Browser-based tracking (Segment snippet, client pixels) is partially blocked by ad blockers — typically 15–30% of desktop traffic. Reverse proxying routes Segment CDN and API calls through our own domain, making them effectively indistinguishable from first-party requests.

Wander's codebase already has proxy env vars wired up (NEXT_PUBLIC_ANALYTICS_CDN_URL, NEXT_PUBLIC_ANALYTICS_API_HOST) but the server-side route rewrites are not yet configured. Activating this is a single engineering task.

Script Proxy value Why
Segment High Ad blockers target segment.io domains specifically. Proxying through wander.com/cdn/... bypasses this. Estimated 15–25% lift in event capture rate. All downstream destinations (Meta pixel, Customer.io, GA4, Amplitude) benefit from one change.
Meta pixel Medium CAPI already covers iOS and a portion of ad-blocker users. Proxy adds recovery for desktop ad-blocker users on top. Not urgent given existing CAPI coverage.
Amplitude / Mixpanel Lower Internal product analytics. Missing events here hurts product decisions less than attribution. Both offer self-hosted SDK paths if needed later.
HubSpot / TikTok / Bing Not recommended now Marginal gain vs added complexity. Proxying Segment captures events for most of these anyway.
Decision needed Approve activating the Segment proxy rewrites — the env vars are already in place, this is one engineering configuration task. This recovers measurement signal across all Segment destinations simultaneously for low engineering cost. Recommended: yes.

Data hygiene: deprecated source with live destinations. There is a Segment source labelled "DO NOT USE, GOING TO BE DELETED" that still has live destinations enabled — including Impact.com (affiliate commissions) and Customer.io. This creates a real risk of double-counting commission payments. This is an engineering task to clean up — flagging for awareness only, no CMO decision needed.

The /listed question — supply vs. OS user
Align on: are these the same funnel, and how much to invest in /listed

Two acquisition pages, potentially two different audiences:

Page Value prop User Destination
wander.com/listed "List your property on Wander" Host seeking marketplace distribution. High bar — Wander is exclusive. Wander marketplace listing → app.wander.com
wander.com/os "Build your direct booking site" Host seeking tech independence. Lower bar — they may never list on Wander. WanderOS direct booking site → app.wander.com

The complicating factor. New marketplace supply is increasingly coming through OTA integrations, not direct host applications. /listed may be becoming a secondary path even as WanderOS grows.

These audiences are not mutually exclusive — but they're not the same. A WanderOS user building a direct booking site is not necessarily interested in Wander's curation process. And a host applying to /listed may not want or need WanderOS.

Decision needed Is /listed an actively invested acquisition channel in 2026, or maintenance mode? And what's the intended relationship — do we push OS users toward /listed as a natural upgrade path, or treat them as genuinely separate audiences with separate campaigns?
06
Message streams — the coordination problem
Align on: vocabulary, suppression rules, ownership

We have six messaging streams running in parallel with no shared rules about who talks to a user, when, and what happens when two channels want to reach the same person at the same time.

Stream Tool Owner Purpose
Onboarding Customer.io Growth Welcome, nudge to first booking
Newsletter Customer.io Brian Weekly blasts, destination guides
Property Recs Customer.io Growth Eng Personalized recs based on browsing
Sales Outreach Outreach Sorrell / BDRs 1:1 outreach for high-value leads
Transactional Backend Engineering Booking confirmations, check-in
Concierge Manual Nick Waze 1:1 trip planning and VIP support

The problem. A user books a trip and receives: booking confirmation, a personal concierge message, an automated newsletter, and a property recommendation — all within 48 hours — all feeling like they come from different companies. We have good tools and good people. What's missing is shared suppression rules between them.

The fix is not complicated. Add lifecycle attributes to Customer.io (in onboarding, in sales sequence, has active booking). Use those to suppress the right channels at the right times. Four phases, ~8 weeks. Full plan in message-streams-proposal.md.

Decisions needed 1. Does this six-stream vocabulary match how you think about our comms?
2. Approve the suppression rules (hard vs. soft).
3. Confirm ownership: Brian owns CIO changes, Sorrell owns Outreach webhooks, Engineering owns the sync layer.
